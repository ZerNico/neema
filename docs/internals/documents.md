# Documents

Documents are editable Markdown artifacts owned by one conversation or one [project](projects.md). They are separate from knowledge documents: they are working material, not indexed source material. A chat's document lives and dies with its answer; a project's is shared by the members and deleted explicitly.

## Storage and transcript boundary

- A document is a ProseMirror tree whose edits the server orders (`prosemirror-collab`). `documents.snapshot` holds the tree as of `snapshot_revision` and `document_steps` every step after it, one row each. Steps are kept long so an editor that was offline can still rebase: they are folded into the snapshot only past 2,000 steps, and then only those older than 30 days. Nothing derived from the tree is stored beside it, Markdown included: a copy would be a second truth to keep in step with every write and to cap. Markdown is made only where it is wanted: Copy, export and the model's view.
- Browser and server build the tree from one extension list (`documents/editor/extensions.ts`). The server rebuilds every step against that schema and refuses a batch with one it cannot apply, so a node or mark one side lacks never reaches anyone. Markdown is an export and what the model writes, not the limit of the schema: a planned section (`pending`, an intent and no text) writes no Markdown at all. There is still no underline, colour or alignment.
- Every block carries a permanent `id` the model points at. Editors mint them for what people type (Tiptap's UniqueID, skipping steps received from the server); the server gives them to everything it builds from Markdown and, after each person's batch, repairs a missing or repeated one with a step of its own. Table rows and cells have none: a table is reached as a whole.
- A tree built from Markdown has no IDs and no empty paragraphs. Before it is compared with the current tree it takes over the IDs of the blocks it matches (unchanged ones at either end, same-type ones in place in the changed middle) and keeps the empty paragraphs outside the change. Without that, every block would differ by its ID alone and a write would replace the whole document, taking any typing in it along.
- Markdown is the canonical form the serializer writes; parsing and writing it back is stable, and our overrides exist where upstream was not (a backtick in code, a fence in a code block, a pipe in a table cell). Raw HTML stays text, empty paragraphs write nothing, and a numbered list cannot hold tasks. A table may have no header row, or a header column, which only the tree holds: its Markdown writes the first row as the header line Markdown requires.
- Formulas are LaTeX in KaTeX-drawn nodes: `$…$` inside text and `$$` lines around a display formula (`<math>` in the model's view). Inline math follows Pandoc's rule, no space just inside the dollars and no digit after the closing one, so prices stay text, and a `$$…$$` mid-sentence, as models write, is inline too. Every typed dollar is escaped when written, as upstream escapes `*`: a pair split by formatting would otherwise come back as a formula, and one text node cannot see its neighbours. A formula a digit follows is written `$$x$$`, since `$x$2` reads as a price. Upstream's tokenizers did neither, which is why `editor/math.ts` replaces them.
- `revision` is the number of steps applied, which is also the version every editor rebases against. To the model it says the text moved and guards nothing. Authorization requires both the owning conversation and the person's [document grant](feature-policy.md); a document owned by another account or unavailable under policy is reported as not found.
- `DocumentService` is the only writer, for people and the model alike. It keeps each document's tree and its steps since the snapshot in memory and runs every read-modify-write of one document alone. The entry moves only after a write commits, so a failed write leaves memory and rows in step; a stored revision that moved without this process drops the entry and the next use rebuilds it. This assumes one server process, as the rest of the app does.
- A chat's document records the assistant message that created it. Editing a message before that answer removes the answer and PostgreSQL cascades to its documents. Retrying the creating answer keeps its message id, so the retry transaction explicitly removes its documents before generating again. The confirm dialog names that loss before it happens.
- Documents carry no citations: the policy keeps `[^N]` markers out of them, since sources are numbered per conversation and nothing in a document resolves one. Sources belong in the chat reply. A citation system for documents would be its own design.
- Document bodies never enter message text, durable tool arguments/results, chunks or compaction summaries. Document tool rows keep only a bounded activity projection such as id, owning conversation, title, revision and outcome. Continuation parts replace tool content with a pointer to application-provided document context.
- In the answer, a created document is a card, the thing the person receives; every other call is a step of the work line, back-to-back calls on one document folding into one step (`assistant-body.ts`). A step names its document only when the answer touched more than one, since the card already names a lone one. A run reads as failed only when none of its calls succeeded: a retried edit is not news. Prose between calls splits the line, which is why the policy has the model fill a planned document without writing between sections.
- Branching copies historical tool rows but never copies canonical document rows. Their references therefore render as inert “From another chat” activity in the branch.

## Model context and writes

- The model reads the focused document as XML: one element per block with its `id`, text as inline Markdown (what it also writes), planned sections as `<pending intent/>`, the person's selected blocks named on the document. A generation gets that view plus a manifest of every other document. Every way a message is sent carries `openDocument`: the document open in the panel, which supplies the initial focus, and the IDs of the blocks selected in it (none for a bare cursor), which the view names. A steer carries its own and moves the focus when it joins the answer. An explicit read or write then moves it again.
- Text in the view is XML-escaped, so text reading `</p><p id="…">` stays text; a `find` quoted with the entities still matches. Markdown itself writes `&`, `<` and `>` as they are, with a backslash only where one would start a tag or an entity (upstream wrote entities, which leaked into exports and were escaped twice in the view).
- The view is budgeted at 24,000 characters of XML. A long document is a window of whole blocks with a `<gap/>` either side and a `fromBlock` continuation; a single block larger than the window comes in parts with `fromCharacter`, and is never counted as read whole. The answer's first view, note included, stays in every request for caching, so a later window arrives as an update and each read's own result says where its window ends and what to read next. A model following the first note again would otherwise read the second window forever. Gaps list the headings they leave out, and an edit can be placed without reading there: `target: "end"` or `"start"` for the document's ends, `position: "end"` on a heading for the end of its section. These become a block and a side before anything else sees the edit, so the preview and the guards treat them as any other; the decoded call finds its preview by the placement it named, since by then "end" is the preview's own last block. After a write the window moves to what was written: left where it was, a write past it never showed, and the model, seeing no trace of its work, wrote it again. Claude's own Docs tools work the same way, inserting at the root's end rather than after a block they must first find.
- The first view of an answer stays byte for byte in every later request so the cached prefix holds. After a write, a separate update message carries the changes since that view: changed and added blocks whole, removed ones by id, cumulative, so a request that drops an earlier update loses nothing. Removed means gone from the document, not out of the window. Past half the document's size, or when kept blocks changed order, it sends the whole view instead. A document focused partway through the answer is not in that first view, so its own first view is repeated ahead of its changes in every later update. When the person's selection lies past the first window, the view opens just before it, as far back as still reaches it. At an unchanged revision, a view that reads differently from the last one sent (a steer's new selection, a window moved) is sent whole.
- An edit names blocks by id (`target`, `through` for a sibling range, `position` replace, before or after, Markdown `content`, or a `pending` intent), or changes text inside one block with `find`. Markdown is fitted to where it goes: a list's items for a list, blocks for the document. A same-type single block replaced in place keeps its id; new blocks get fresh ones.
- Replace and delete are guarded by what the model has seen: each block's fingerprint (its whole subtree, attributes included) as last shown. A block the model was never sent, or one a person changed since, is refused as `conflict` and nothing is written. Only a request actually sent counts as showing a block: `streaming.ts` hands the tools each prompt it sends, never a render made for the budget or a comparison. `find` needs no guard: its text is the check. Refusals are fixed sentences, since tool results persist; the current content reaches the model only through the view.
- `create_document` takes Markdown and an `outline`, each entry a planned section; the policy has the model create a skeleton, then fill one section per call by replacing its `pending` block.
- Creation and every write run the generation guard first inside the transaction, so Stop, retry, edit and lost ownership interrupt before anything moves. Lock order is conversation, then document.
- Edits stream. An `edit_document` aimed at blocks begins once its target is known and its content starts; the streamed text is released on its own 30 ms beat, a share of what is waiting each time and at least a few characters on to the end of a word, so a provider that sends a sentence per chunk still reads as typing. The decoded call waits for that to catch up, up to two seconds, before it writes the rest. Each write, under the message-row fence (`ensureGenerationLive`), replaces only the blocks the preview itself wrote, found by their ids and checked against the fingerprints it wrote. The rebuilt blocks take the last write's IDs down to list items and cells, so only what differs from the last write is stored, so text lands as the words just streamed and the assistant's cursor follows its end. Every model write fills out a table's short rows before it is stored, a live write before it fingerprints what it wrote: a table still streaming has one, and every open editor's table plugin would otherwise add the cells itself, as that person's edit, racing the others into repeated block IDs. A person touching one ends the preview with their text kept, and the decoded call then returns `conflict`. A streamed `create_document` creates the document once the title has arrived and writes its content as it comes, in the chat, private, until the call says `scope: "project"`: a scope arriving after the content must not have shown it to the project. The decoded call moves it into the project when that is where it belongs. Every creation write names the revision it last wrote, so someone typing into the new document stops the preview, keeps their text, and the call returns `conflict` with the document as it stands; an unclaimed creation is deleted only if nobody wrote in it. An edit preview a person touched is claimed all the same and settles as `conflict`, rather than its text being inserted a second time; a preview that never wrote (a deletion) is applied as an ordinary edit. The SDK runs the decoded call's handler beside the stream still being read, so one lock per generation orders the two: the handler claims its preview and writes the final text under the full fence. A preview no call claims is undone when the round ends: an edit's blocks go back to what they replaced, a created document is deleted. A stopped answer's preview stays as it stopped: the round's end tells an interruption from a finish and only lets go of its previews.
- Tool-call transport accepts an object with omitted keys even when the advertised JSON schema marks them required. The handler, rather than `LanguageModel.streamText`, then returns its bounded invalid-input correction. This is essential for aliases such as `old_string`, which cannot be repaired if Effect rejects the part first.
- Document context is application data, not instructions. Research mode omits conversation documents in the first version.

## Comments

- A thread is a row per comment in `document_comments`, the first one naming itself; its text carries a `comment` mark with the thread's ID, so the anchor moves with edits like bold does and goes when that text is deleted. The thread then stays open without it and shows the `quote` kept when it was started. The mark writes no Markdown. Comments reach every open editor as a `comments` frame on the document feed whenever one changes. A new thread's ID is the client's, refused if another document's thread has it. The assistant's comment writes run its generation guard before taking the document lock, the order every generation write uses. The thread a message was sent from always has a place in the model's view, however many others there are.
- People who may edit can comment, reply and resolve; a comment is deleted by its author, or by anyone who may edit when the assistant wrote it, and deleting a thread's first comment deletes the thread. The assistant never resolves: a thread belongs to the people in it.
- A comment goes to the assistant when it names `@Assistant`, typed or picked, which a new comment in a chat starts with. Sending one is an ordinary chat message (`Comment on “…”: …`, drawn in the transcript as the comment) whose `openDocument` names the thread, so every way a message is sent carries it. The model sees the focused document's open threads in a `<comments>` block, with that one marked `asking` even once its text is gone, and answers in it with `comment_on_document`. A comment sent to the assistant counts as answered once the assistant writes in the thread after it. On a project page, with no chat open, it starts a new chat in the project.
- A model edit that would remove all the text of an open thread is refused as `anchors_affected` with nothing written, unless the call passes `allowDetach`, which the policy reserves for a person asking for that text to go. A `find` edit keeps comments on the words it does not change and moves those on replaced words onto the words replacing them; a whole block rewritten from Markdown keeps none.

## Person edits

- The open editor holds a live connection: `GET /api/documents/:id/stream?revision=` sends the steps since that revision (the whole document as `reset` when it is absent or older than the snapshot), then every later step and cursor. Its own steps come back too: that is how collab learns they were stored. It sends through the `pushDocument` server function, batched every 80 ms, with the revision the steps were made on. Pushes go through a server function rather than a raw route so the CSRF check applies. Document bodies and steps never ride `chat_sync`; cards and lists follow typing through a throttled `document.changed`.
- Steps made on an older revision are refused, never merged blindly. The editor rebases its own over the steps its feed brings and sends again, so two people typing at once land in the order the server took them. A resend of stored steps is refused the same way and stored once. A person's batch locks only the document row, never the conversation: batches arrive several times a second and would otherwise queue ahead of chat writes.
- Unsent steps, the document they were made on and the collab client id are kept on the device (the `document-outbox` namespace of the [device cache](device-cache.md)), so a reload, a crash or a discarded tab does not lose them. The reopened editor rebases them like any others. The entry is one per document on the device, so a tab owns it through a Web Lock: only the owner restores it and takes on its collab id, and another tab works under a fresh id without touching it until the owner closes. Taking over then, it reads the entry from storage, since its own cache was loaded before the old owner wrote (which flushes before letting go of the lock), and keeps the text of whatever was left unsent as recovered, since steps typed under another identity cannot be rebased; a document reopened in one tab while its last connection still flushes carries on with that connection. Two tabs sharing an id would each take the other's steps for confirmations of their own and drift apart. A step that no longer fits (its paragraph was deleted), or a base older than the snapshot, is never dropped silently: its text is kept in the same entry and shown in the panel to copy, across reloads, until dismissed. The namespace is kept, not cached: nothing in it is evicted for the budget or refused for its size. Each connection also saves and writes at once when the page goes or is hidden, since the save timer would not outlive a reload. Recovered text is the stretch the unsent steps changed, applied to the document they were made on, so corrections and repeated words read as typed. A connection that does not own the entry saves under its own key beside it and holds a lock of its own while it lives; whoever owns the document next takes the entries of connections that are gone and keeps their text as recovered. An entry whose document no longer loads (a schema changed) has its words kept as recovered text before it goes. A push acknowledges exactly the batch it sent, not the revision it returns, which a server repair may have moved further.
- The panel stays editable while the assistant answers, and its edits appear as they are stored. Before send, structured answer, retry, message edit or branch, every connection, including one closed moments ago, flushes until the server has its steps; Stop never waits for it.
- A task's tick is the `checked` attribute of its node, so ticking is one small step beside any other edit.
- Cursors are presence, not steps: each editor sends its selection with the revision it is valid at, and others map it through the steps since. One that arrives before its steps leaves the last placeable caret in place rather than removing it. A caret between blocks, as after selecting everything, is drawn at the end of the text before. Carets are an overlay, not decorations in the text, so a caret that moves slides there instead of being redrawn. The server labels every cursor it relays with the signed-in person's name and a colour fixed by their ID, whatever the client sent, so nobody can pose as someone else or put CSS into others' editors. It keeps each editor's latest one for whoever opens the document next and removes it when that feed closes. A feed says `gone` only when its reader lost access; one ended because the entry was rebuilt reconnects and catches up. The assistant has no presence of its own: each editor draws a cursor at the end of what the model's latest steps wrote, fading after a few seconds. The view never moves to follow it: a person reading or writing elsewhere stays where they are.
- The size limits are measured on the tree, by one function the editor and the server share (`overCap` in `editor/limits.ts`): the block cap, the tree's text within the character cap, and attribute text (IDs, intents, links, comment marks) within a budget of its own. The editor refuses a local change that grows the tree past them; a collaborator's accepted change always shows. The server checks every write, a person's as much as the model's, against those limits and against attributes of the right kind: plain values only (a table cell's column widths the one list), a heading level 1 to 6, a list start, a task's checked flag. A block ID not shaped like one is replaced like a missing one, so nothing a client sets reaches the model's XML as markup.

## UI ownership

- `DocumentOwner` mounts one controller per known id at conversation level, above the virtualized transcript and outside the replaceable panel body. Only the document open in the panel holds a connection, which keeps each tab to one document stream; a closed one lingers until the server has its steps, so closing the panel or opening another detail cannot discard typing. The connection owns the editor and the panel only mounts it, so a closed panel can still rebase and send.
- A full document card renders at the creating `create_document` tool row, using that row’s persisted message, turn, call and text-offset coordinates just like other tool activity. Later reads and edits are compact rows. A legacy row without its create call falls back inside its creating answer, never below the transcript.
- The model names a document and anyone who may edit it can rename it, from the panel's More menu or a project's document list; a rename moves no revision and reaches every card and list through `document.changed`. The panel's actions row is the editor's formatting controls, then Comments, More (rename and export) and Copy, one row that never wraps: the editor portals its toolbar into a slot the owner hands both, and controls that do not fit fold into More. A viewer leaves the slot empty. Comments sit at their text: a click on commented text opens that thread there, and the header's Comments button lists them all. There is no separate Markdown view: Copy gives the Markdown. PDF goes through the browser's print dialog on a print-styled copy of the tree, which pages and embeds fonts better than anything drawn here and works the same in the desktop app. Documents are removed by rewinding their creating answer rather than through a panel delete control. Copy and export serialize the local tree, so they wait for the editor to connect, and never add content to the transcript.
- The editor is Tiptap with the collab plugin, loaded with the first open document rather than the chat. ProseMirror's history undoes only this editor's steps: steps received from the server are kept out of it and rebased under it, so undo never takes back another person's or the assistant's change. Formatting comes from the toolbar, a bubble menu over a selection, a `/` menu and a right-click menu (Shift right-click keeps the browser's own), which also holds every table action; every control is a command on the tree, so it syncs like typing. Tasks draw with the app's checkbox through a node view, which changes only the browser's rendering, never the shared schema. A `/` typed by a collaborator never opens this person's menu.
- Dates and people are chips, inline atoms with one value: `[date value="2026-10-09"]` and `[@ id="…" label="…"]`. The model reads and writes those shortcodes, so it can tell a chip from typed text; Copy and export hold the plain date and `@name`, made from the tree's chip nodes, so the same characters typed into a code block stay as typed. People offered are the sender and the project's members.
- Asking from the document plants an empty `pending` block where the person is and sends their request as an ordinary message from the chat, with that block as the selection named when it was asked, not wherever the cursor is when the message leaves. The policy treats a selected pending block with an intent as the place to write, so the answer replaces it like any planned section. While an answer runs the request is refused and the block reverts to empty.
- A viewer gets the editor without controls and not editable. Links are only http, https and mailto, and a link carrying any other scheme renders without its address. A click places the caret, so a link opens on Cmd or Ctrl click, or any click for a viewer, always in a new tab. A `mermaid` code block draws as its diagram in the browser editor, with its source shown while the cursor is in it, and prints as the diagram. The document holds only the source. Math is not rendered.
