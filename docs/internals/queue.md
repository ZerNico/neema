# Queued messages and steering

A message sent while an answer is generating becomes a queue entry instead of being refused. Entries wait behind the one live generation per conversation; the queue only decides what starts next and never weakens that rule. Steering hands a queued entry to the generation that is running now instead.

## Promotion

- `conversation_queue_entries` rows are future work, not transcript rows. A branch copies history and never a queue. Conversation deletion releases queued files explicitly, because both link tables cascade but the attachment rows they point at do not.
- `promoteNextQueuedTurn` opens a turn in the same transaction that consumes the entry. It locks the account before the conversation, like every attempt, and rechecks account eligibility inside resolution before commit. Entries start steered first, then oldest first (`queueOrder`), and the strip lists them in that order. A duplicate dispatch or a racing send finds either a busy conversation or an empty queue, never a second turn.
- Dispatch validates one entry and its monotonic `revision`. Promotion compares both under the conversation lock and resolves choices from that locked entry. Replacement advances the revision with its options and file links in one transaction. A validated explicit steer advances it too, so older dispatch validation or failure annotation cannot undo the new target or release. A changed head or revision refuses promotion without consuming files. A later dispatch validates the new snapshot.
- Automatic progress runs only after an answer ends cleanly. A stop or a failure pauses the queue, since the person stopped the conversation and not just one answer. An unanswered `ask_user` holds it too: the structured answer owns the next turn. A person pressing **Send next** may start after a stop or failure, never ahead of a question.
- `readQueueGate` is the one reading of those rules. Promotion refuses by it, and the conversation loader turns it into `queueState` for the strip, so what the strip says is what promotion will do.
- Three things try to start the next entry, all through the same transaction: the generation's settled hook (`GenerationSettled`, handed in by the service because the engine cannot reach it), a sweep for queues a restart left waiting, and an attempt straight after queueing, in case the answer ended while the request was in flight. A failure marks only the selected entry and revision, never a reread of the head. Replacement, validated explicit steering or removal makes that late annotation a no-op. The sweep's interval is `QueueSweepInterval`; the streaming integration suite sets it to `null` so no background start races what a test asserts.
- Nonnull `last_error` is a durable hold for every automatic dispatch and steer claim, not just the sweep. Imports use it to retain text and files without starting work. Enqueue, completion, editing a different entry and ordinary desktop dispatch cannot release it. Only selected **Send now**, replacing that entry, or a newly validated explicit steer releases the selected work. An account refusal holds its queue too. Restoring access alone does not run it.

## Chats with a computer

- A queued message in a chat with a computer starts like any other, from the server, wherever it was queued. Its local calls go to the chat's machine when they run, so a machine offline by then answers them as offline. Queue entries store no machine state, since it can be stale by the time an entry reaches the front.
- Files sent with a queued message are attachments like any other and land in the workspace when a call first runs after promotion ([desktop](desktop.md#files-into-and-out-of-the-chat)).

## Steering

- A steer marks an entry with the running generation's message and generation id. The generation claims it only at a tool boundary: a model call ended in tool calls, every result is terminal, and the model is about to be called again anyway. It never cuts a stream. The SDK starts a tool the moment its call is parsed, ahead of the loop reading the stream, so a cut could kill a tool mid-flight; Codex and LibreChat inject at the same boundary for the same reason. Nothing is claimed on the last round, which has no call after it.
- An answer that ends without another step never has a steer bolted on. The entry keeps its steer fields, and the queue orders steered entries first, so it goes out as the next turn ahead of older messages; after a stop, a question or an error it waits first in line. The claim matches the live generation id, so a later attempt never takes a stale steer. [Resuming](resume.md) the answer is the one exception: the same answer continues, so its claim moves the steer to the new generation.
- **Send now** is the one way to cut an answer short for a queued message: `sendQueuedNow` stops the running answer, keeping what it wrote, waits for `awaitSettled`, then promotes that entry with `jumpQueue`. A paused queue just starts it.
- A claim is fresh input admission in its own transaction. It checks account eligibility before taking the generation fence, keeping the account-first lock order. Refusal holds only matching unheld steer entries, retains their text and files, and publishes queue-changed without failing the already accepted answer. Restoring access alone does not release a hold. A stopped, retried or reaped attempt is interrupted at the fence and leaves every entry unchanged.
- A steer belongs to the attempt it was delivered into, like that attempt's tool rows. The claim records where it arrived, the answer's text offset and the round it followed, and the display draws it inside the answer there: the text above was written before it, the text below after. It is never a transcript row of its own, and it cannot be edited on its own. A branch copies it with the answer, pointed at the copy; the link cascades if the answer is deleted.
- A steer keeps its real time, so in the one order everything reads, `(createdAt, id)`, it sits just after the answer it went into: that answer began before it, and nothing else can join the conversation while it runs. Retrying the answer or editing its question deletes everything after the answer, steers included, with no special case; the confirmation names them first. Resuming it keeps them, placed in the continuation where they arrived. A branch through the answer reaches past it for them. Anything asking what came last, the question a reply answers or whether the queue may start, reads turns without steers (`turnMessagesOf`, and the client's `turnMessages`), so a steer never stands between an answer and the reply to its questions.
- The engine writes a `steer` chunk right after the claim, through the same persist-then-publish path as tool markers, so the answer shows it in order live and a resume replays it in place. The live answer merges streamed steers with stored rows by id; a lost chunk costs nothing, since the rows are the record. The chunk names its queue entry, so the strip drops that row before the refetch.
- The live continuation receives a steer as the next user message after the round it followed, and that one call's trailing reminder says it arrived mid-task: a bare user message after tool results reads like a new turn, and models answered it and stopped. Later turns read it the same way: `buildHistoryMessages` renders the steered answer as one history group, the answer so far, the steer with its files as native parts or extracted text, then the rest, split at the text offset or between replayed turns. Compaction and budgeting treat that group as one unit. Steering checks the files against the running answer's model first, which may not be the one the entry was queued with.

## Files

- Queued files are claimed through `conversation_queue_entry_attachments`, a second owner kind beside `message_attachments`, never through ids in the entry's input. Promotion and steering move the link to the new user message in the transaction that creates it. The attachment row and its bytes stay, so a move never produces cleanup work.
- Postgres cannot put one unique index across two tables. Exclusivity comes from `claimAttachments` locking the blob rows before checking either table, the same order every reference writer follows. Without that lock, a send and a queue racing for one upload could both win; the attachment integration suite proves this by removing it.
- Removing an entry deletes its files through the usual orphan path, with byte deletion after commit. The sweep for abandoned uploads and the upload-delete endpoint both treat a queued file as claimed.

## Editing

- Edit reopens an entry in the composer and saves it with `replaceQueueEntry`, which keeps the row's id and so its place in the queue. Its files are reconciled like an edited message's, and any pending steer is dropped, since it was aimed at the words being replaced.
- The row stays durable until the replacement commits, so a reload or a closed tab loses nothing. Seeded chips are marked existing: removing one only drops it from the replacement, and cancelling never deletes the entry's files. Edit opens only from an empty composer, because seeding replaces the draft and its uploads.
