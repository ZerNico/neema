# App review (2026-09-24)

Read-only audit notes for `apps/web` and `apps/desktop`. This is a living review, not an exhaustive file-by-file security certification. The first findings were challenged by a fresh, independent read-only agent against the call chains and installed Better Auth 1.7.3 implementation. Separate fresh agents challenged the chat-lifecycle and integration-permission findings against their server and client paths. None of those passes reproduced a concurrency race, process crash, lease-expiry UI scenario or pending-approval interleaving. Do not treat passing existing tests as coverage of those scenarios.

## Prioritized findings

### 1. First-user admin bootstrap is not serialized — confirmed

`apps/web/src/modules/auth/server/config.ts:155-167` counts users in the `user.create.before` hook and assigns `admin` when the count is zero. Distinct concurrent signups can both observe an empty table and both become approved admins. The auth adapter does not serialize these signups and `apps/web/src/db/schema/auth.ts:8-20` has no constraint preventing the second admin. High impact, limited to the empty-instance signup window. Add an isolated concurrent-signup regression test before changing the bootstrap rule.

### 2. Missing approval records fail open after signup failure — confirmed

The `user.create.after` hook in `apps/web/src/modules/auth/server/config.ts:169-176` writes the approval record after Better Auth has created the user and credential account. The installed adapter has no real transaction for this flow; its queued after-hook runs after those writes. If the approval write fails or the process exits in the gap, the account persists. `apps/web/src/modules/auth/server/auth.ts:90-94` and `signup-gate.ts:32-38` treat a missing record as approved, so the account can sign in after recovery despite an approval policy. Existing users were backfilled by the approval migration; the missing-row fallback should not silently grant access to newly created accounts. Test an injected after-hook failure and subsequent sign-in.

### 3. Pending integration calls can outlive a block or admin disable — confirmed by independent code reviews

`apps/web/src/modules/integrations/server/tools.ts:88-125` reads a tool’s permission before waiting for approval, but proceeds to `adapterTool.run` after an “allow” answer without reading it again. If the owner changes a modifying tool such as Outline’s `create_document` to **Block** in Settings while its approval card is pending, then approves that card, the tool still runs (Outline creates and publishes the document). The Settings write persists immediately, while `decideIntegrationCall` only checks ownership of the pending call. Separately, an admin can turn the integration off during the wait: new offers are refused, but the captured session remains usable because `service.ts:269-289` checks only whether its connection is active, not whether the integration is still enabled. That contradicts the admin UI’s promise that turning it off stops chat tools. Recheck both current tool permission and integration availability at the post-approval execution boundary; test both interleavings. These findings are based on independent adversarial call-chain reads, not live reproductions. Disconnecting the person’s connection *does* stop the external RPC through a fresh bearer lookup; Stop and timeout address other cases.

### 4. A crash and retry can permanently block research admission — confirmed with timing condition

The message’s generation lease lasts 45 seconds (`apps/web/src/modules/chat/server/repo.ts:265-271`), while an active research run’s lease lasts 60 seconds (`research/repo.ts:385-405`). After a process crash, the message can be reaped while the research lease remains live. If the person retries that same assistant message before the research lease expires, the retry assigns a new generation ID; the expired research run’s later `finalizeTx` rejects the old generation before making its run row terminal (`research/repo.ts:127-140,357-372`). Admission and a partial unique index continue to treat that `running` row as active, so new research for the user is refused until the affected row is deleted. A fresh adversarial reviewer confirmed this specific ordering, not a failure on every crash; no crash/retry sequence was reproduced. Settle the expired run and run-scoped accounting even when its message has since changed generation, without writing into the new attempt; test reap message → retry → expire run → reap run → admit research.

### 5. Reusing a blank draft can change its settings without a revision — confirmed, narrow race

`apps/web/src/modules/drafts/server/service.ts:160-180` can apply model-supplied changes to an existing blank draft while keeping revision 1 and reporting the operation as a read, so `draft.changed` is not published (`service.ts:208`). An open editor receives no invalidation. Its normal Save fetches the latest draft and detects changed fields, but a write landing *between that fetch and the Save revision check* can let an older editor save settings its user never reviewed. A fresh reviewer confirmed that narrower interleaving, not an unconditional unseen save. Treat a changed reuse as a revision-incrementing write with a notification; keep an identical reopen read-only. Test an editor Save racing a model change to a reused blank draft. The focused draft-reconciliation test passed 4/4 but does not cover this race.

### 6. Claimed scheduled fires can disappear without a run record — confirmed

`apps/web/src/modules/schedules/server/repo.ts:233-271` advances `nextFireAt` in a transaction, including setting it to null for a one-shot. `service.ts:115-124` starts the fire only after the claim, in a detached fiber; `service.ts:82-109` inserts `schedule_runs` after the fire. A crash in that window permanently loses a one-shot without a recorded attempt; a defect in the fire can also skip the record. Recurring schedules lose that occurrence. Consider a durable pending attempt in the claim transaction with explicit recovery/terminalization, and test a claim followed by an interrupted fire.

### 7. Lease reconciliation can leave a live chat stuck streaming — confirmed

`apps/web/src/modules/chat/server/streaming.ts:364-387` publishes a reaped generation’s `done` without its `runId`. The server subscription accepts that event (`streaming.ts:2965-2977`), but `apps/web/src/modules/chat/client/use-message-stream.ts:991-999` treats the missing ID as a different attempt, closes the SSE connection and refetches without setting its stream state to terminal. A second reaper in `apps/web/src/modules/chat/server/conversation-detail.ts:8-25` publishes only a sync invalidation, not an SSE `done` at all. If either reaper settles a row while a tab is subscribed, the row correctly becomes `error`, but `chat-view.tsx:673-681,1140,1740,1813` keeps that tab’s sticky overlay at `streaming` and disables its composer even after the detail refresh. Reloading the page recovers. Preserve the reaped generation ID in terminal events and reconcile live stream state with a terminal detail row; test both reaper paths with an already-open subscription and a refreshed view. This is a client liveness defect, not a duplicate-write or access-control issue.

### 8. Failure before the generation loop delays settlement — confirmed

`apps/web/src/modules/chat/server/streaming.ts:419-540` reads the generation config, policy, tool offers, model and history before the `generate`/`flusher` race and its error finalizer at `streaming.ts:2794-2807`. A missing generation config or a failed database read there ends the detached fiber; `startGeneration` clears its in-memory registration (`streaming.ts:2850-2884`) but leaves the message `streaming`. Stop finds no local generation to cancel, and the conversation rejects new turns until the 45-second lease expires and a reaper settles it (potentially another 10 seconds on the timer). Ensure startup failures finalize or terminalize the fenced attempt immediately, and test a preflight failure after the assistant row is committed. The stale-live-tab behavior above can extend the visible failure until reload.

### 9. Cancelling the desktop server chooser stops Work without switching — confirmed

With Work active, confirming **Switch server** calls `disposeWork()` before the address chooser opens (`apps/desktop/src/connect-flow.ts:48-54`). That aborts in-flight desktop calls, stops owned processes and replaces the execution session (`main.ts:280-285`, `executions.ts:129-135`). If the person then cancels the chooser, the current server window stays in place but Work has already stopped. **Keep working** at the first confirmation does prevent this; the defect is specifically cancel-after-confirmation. A fresh agent checked the actual chooser and disposal paths, including the user’s uncommitted desktop changes; no GUI reproduction was run. Defer disposal until a valid new server is accepted, while keeping the warning before the irreversible switch, and test cancel after opening.

### 10. Dirty deletion can block exit after an agent is gone — confirmed; schedule outcome differs

Both the agent and schedule editors delete first and then navigate through their ordinary unsaved-changes blocker (`apps/web/src/modules/agents/ui/agent-editor-page.tsx:97-99,160-174`; `schedules/ui/schedule-detail-page.tsx:158-174,251-253`). If an agent has unsaved edits, the person confirms Delete and then declines the separate **Discard unsaved changes?** prompt, navigation can be blocked after deletion; cached agent detail can leave the deleted editor visible. The schedule has the same unnecessary second prompt, but a failed post-delete refetch normally replaces that editor with **Could not load this schedule**, not a persistently visible deleted editor. A fresh reviewer checked installed router behavior; tests mock the blocker and do not exercise this sequence. Handle dirty-state confirmation before deletion or bypass the blocker specifically after successful deletion, and test both editors with dirty forms.

### 11. Draft endpoints accept the owner's other draft kind — confirmed, bounded

`apps/web/src/modules/drafts/server/repo.ts:108-115,135-153` checks that a draft belongs to the user’s conversation, but not that its kind matches the agent or schedule endpoint used. The kind-specific services then cast the returned row to their own type (`agents/server/draft-service.ts:30-36,177-183`; corresponding schedule service). A caller who knows one of their own schedule draft IDs can read, patch or discard it through agent-draft endpoints (or vice versa), including when access to that draft kind’s authoring feature has been revoked; a wrong-kind Save may instead fail on an assumed field. This is **not** cross-user access, and live-resource writes retain the called endpoint’s checks. Require the expected kind at each get/lock/discard operation before casting or writing; test wrong-kind IDs under both feature policies. Independently checked by a fresh reviewer; no exploit test was run.

### 12. Invisible jump-to-bottom control remains focusable — confirmed

At the bottom of a chat, `apps/web/src/modules/chat/ui/virtual-message-list.tsx:128-141` leaves a native **Jump to bottom** button mounted and labelled, hiding it only with `opacity-0` and `pointer-events-none`. It remains in keyboard and screen-reader navigation; activating it while scrolling can leave focus on an invisible control. A fresh check confirmed the Button’s behavior and found no alternate jump control; existing tests assert opacity and clicks, not hidden-state accessibility. Mark the button inert while `atBottom` to preserve its fade without exposing an invisible interactive control. This was not tested with a screen reader.

### 13. Queued-message edit resets an unsent search choice — confirmed, low priority

`apps/web/src/modules/chat/ui/use-conversation-queue.ts:162-165,204-224` saves and restores model and reasoning effort but resets search to its default on edit end. If a person opts out of search on an otherwise empty composer, edits a queued message and cancels, the opt-out is lost. The composer requires an empty draft before edit, so no unsent text is lost. `use-conversation-queue.test.tsx:150-171` currently expects the reset rather than restoration.

### 14. Interrupted filesystem uploads leave untracked temporary files — confirmed, low frequency

`apps/web/src/modules/attachments/server/fs-blob-store.ts:68-79` writes a random `.tmp` sibling before renaming it to the canonical blob key. An ordinary failure removes the temporary file, but a process exit between those operations cannot. The cleanup intent tracks only the canonical key (`attachments/server/service.ts:112-120`), and reconciliation deletes only that exact key (`fs-blob-store.ts:89-96`), so the temporary file survives startup and periodic cleanup. Each interrupted upload is size-bounded (attachments and knowledge at 20 MiB); repeated interrupted uploads can accumulate disk usage. A fresh agent independently checked the write, cleanup and tests; no crash was reproduced. Sweep only old files matching this writer’s exact temporary naming scheme, without deleting a live write; test planted old and fresh temporary files.

### 15. Agent-draft discard omits its authoring policy — confirmed, low impact

`apps/web/src/modules/agents/server/draft-service.ts:300` lets an authenticated person discard their own agent draft without checking `agentsCreate`, unlike agent-draft get/open/patch/save/reload and the corresponding schedule discard. After their agent-authoring permission is revoked, they can still delete that draft by ID. It does not delete a saved agent or another user’s draft, but conflicts with the documented suspension of authoring operations. Apply the policy guard to discard, preferably at the write boundary, and test revocation before discard. A fresh reviewer confirmed the narrower scope; no targeted regression test was run.

## Conditional observations, not prioritized security defects

- `apps/web/src/routes/api/files/$attachmentId.ts:50` marks authenticated attachments `private, max-age=31536000, immutable`. A browser can retain bytes after attachment deletion or an account switch, but normal UI does not reveal another account's opaque attachment ID. Treat this as a low-priority cache-retention/privacy decision, not a straightforward cross-account exploit. Compare the `no-store` policy for knowledge downloads.
- `apps/desktop/src/grants.ts:35-40` scopes grants by server origin and conversation ID, not app account; a same-origin page with a known old conversation ID can request those local grants through the bridge. This is not a demonstrated privilege escalation when both accounts share the same desktop/OS profile and its filesystem authority. Document the trust boundary if per-account isolation in one desktop profile becomes a product requirement.
- Stop cannot cancel a newly restarted process’s unexpired streaming row: its in-memory registration died with the old process, but `stopGeneration` only reaps rows whose 45-second lease has lapsed (`service.ts:1791-1821`, `streaming.ts:2887-2896`). The existing integration test deliberately treats a fresh lease as live. This is a bounded availability tradeoff for uncertain cross-process ownership, not a separate unbounded defect. A sliding PubSub can also drop chunks for a pathologically stalled subscriber; ordinary replay/reconnect and terminal refresh repair that case, so no general missing-chunk finding was established.

## Structure and test quality

- `apps/web/src/modules/chat/ui/chat-view.tsx` mixes both chat views, projection, and mutation orchestration. Extract cohesive responsibilities when working in that area, rather than splitting solely by length.
- `apps/web/tests/integration/streaming.test.ts` covers several distinct domains in one large suite. Separating them could improve focused runs, but its shared gateway/fixture must be extracted carefully and each new integration file starts its own Testcontainers database. No redundant tests were verified; do not delete tests based on size.
- The domain-based folder layout is generally coherent. No wholesale restructure or dead-code deletion is justified by this pass.
- The production startup check in `apps/web/scripts/check-production-start.mjs:67-75` accepts any status `>= 400` for three deliberately missing API/server-function/asset paths. A regression returning a generic 500 without a shell could pass those probes. A fresh review confirmed this narrow negative-probe gap, but rejected describing the script as a general registered-API health check: its main shell routes do assert exact statuses. Prefer exact expected 404s (or another observed intentional 4xx); no build was run to establish their current status.
