# Deep research

Deep research is a tool the model calls on an ordinary turn (`research/tool.ts`), not a mode of the conversation. The one fact that shapes everything else: a run is a unit of work owned by the `deep_research` call that started it, not a kind of generation. The host turn writes the brief and the answer; `research/runner.ts` and `research/execution.ts` only investigate that brief and never see raw history, memory or the answer sink.

## Run identity

- A run is fenced by the generation that started it (`research_runs.generation_id`) and its own lease. `messages.generation_id` already changes on retry and edit, so that is the whole invalidation rule — there is nothing on the message to clear, and a message can hold several runs.
- A call id and a run id are different values. The observer mints the row, the handler starts the run, and only the envelope's own `runId` correlates with the progress it carries; the client must not check one against the other. On the mode path they were the same value, so code that compares them looks right and silently drops every live update.
- The run points at its call (`research_runs.tool_call_id`), never the reverse. The handler cannot learn its own row id from the toolkit, which hands it the provider's call id, so the stream observer mints the row and releases the handler through the same deferred handshake the desktop tools use. `message_tool_calls.research_run_id` on a _child_ row means "produced inside this run"; the owning row leaves it null.
- **Ending a run must not touch the message or any other row on it.** The run is one call inside a turn that continues afterwards, and the generation's own completion path owns the message, its text and its other calls. The only row outside `research_*` that finalization writes is the run's own call, whose body is the run's. Erroring siblings from here is what once ended the turn that made the call.
- The composer toggle only _offers_ the tool (`message_generation_config.research_enabled`); the model still decides whether to call it. The offer requires both deep-research and web-search [grants](feature-policy.md); workers receive a brief, not an independent permission to search. Retry keeps the choice the attempt ran with, edit takes the submitted one — the same rule as search. Answering a clarification and editing are their own submissions and neither surface offers the toggle.
- A second call while a run is active is refused as a tool result (`outcome: "unavailable"`), never a failed turn. Admission is one active run per person, through an advisory lock and a partial unique index.
- Research writes hold the conversation lock and validate current run/owner/lease. Expired research is terminalized, never auto-resumed: the fenced ten-second heartbeat is the fallback ownership check and the process-wide reaper owns expiry. Settlement is run-scoped even if the message was reaped and retried first; otherwise the old active row blocks admission indefinitely. It may update the run’s own call and ledger, but never the retried message or its new attempt. Stop cancels whatever run the attempt started, keyed on the generation.
- A run's ordinals live above every reachable host turn (`RESEARCH_TURN_BASE`), and each run starts past the positions earlier runs on the same message used. Child rows share `message_tool_calls` with the host turn, and that table is unique on (message, turn, call); the transcript hides them behind the call anyway. Reading the earlier runs' highest position is safe because a user has one active run at a time, so runs on one message never overlap.

## Ownership split

- The host turn owns the conversation, the brief and the answer. `research/runner.ts` receives only that brief plus a separately built investigation execution object — no raw conversation history, memory snapshot or answer sink. `execution.ts` structurally bars the investigation from the answer sink.
- `RESEARCH_APP_POLICY` goes in the system prompt wherever the tool is offered, and must rank it against the web tools. Without it the host reads only the web hint, which says to use `web_search` for current information, and reaches for the cheaper tool on exactly the questions this one exists for. It states that the person asked for research, not that the model must comply: declining stays a choice it has to own out loud.
- Clarification is the host's own `ask_user`; there is no separate clarification stage. The offer therefore has to survive one: a send that continues an earlier attempt keeps that attempt's `research_enabled`, exactly as search does, or the model asks and the answer lands on a turn that can no longer research. `RESEARCH_APP_POLICY` has to say asking is worth it, because the `ask_user` hint discourages it by default and a run cannot ask once it starts. The tool description tells the model to resolve a consequential ambiguity before calling, because the workers cannot ask anything.
- If the first coordinator returns no assignments (including an immediate `finish_research`), the brief itself is admitted as one task through the normal budget/worker path — merely calling the coordinator does not guarantee investigation, since simple questions made it finish before any report existed.
- Task-relevant remembered constraints can enter the brief through model selection; that is context isolation, not a guarantee against semantic disclosure by the host model.
- `research/execution.ts` keeps one budget, lease/fence, deadline and accounting stream for the length of the call.
- The host keeps its ordinary toolkit, including memory and [agent drafts](knowledge-and-agents.md#conversational-drafts); coordinator, workers and reporting receive none of it, nor private settings.

## Transcript and panels

- A run is a card in the transcript, the one tool call drawn as more than a row: a run lasts minutes and is worth following. It shows the run's title, the pages it has gathered so far and a clock, then the count and how long it took. The count is the run's own pages, the same number the panel shows. It settles when the call returns, not when the message completes; the answer streams below it with the ordinary "Thinking…" state. The card opens the run's activity panel (`research-panel.tsx`), keyed by the call's position in the message rather than the run id, so it opens while the run is still starting. The panel is milestones first, with the log one click away: the plan, each topic once work on it starts (what it is on now; once finished, its finding and how many sources it found), then the sources by site. Each milestone opens to the searches and reads behind it, drawn through the transcript's `ActivityFace`. While the host writes the brief, a writing marker shows the card as starting. The host passes the `title` and `language` because the coordinator never sees the conversation: the title is shown on the card and the panel, and the language sets the task titles. A run without a title reads as "Deep research".
- The detail panel snapshots its body at open; `ResearchPanelOwner` refreshes body/subtitle in a commit effect from the final persisted/live display. Selection is message + the call's position, independent of bubble mounts. A tab binds to the first run it sees there, so the run replacing the starting placeholder fills it, while a retry's placeholder or run at that position closes it. Stale chunks never arrive because the stream is fenced by the generation. Identity-checked refresh cannot reopen a closed panel or replace Sources. There is no module-level message cache or render-time publication.
- The sources panel lists sources without an extraction badge: whether a page was read or only snippeted is model-facing (`evidenceManifest`), not reader-facing. Briefs and worker reports never render. The one exception is a finished topic's finding: the report starts with a `Finding:` line in the person's language, and `finding.ts` splits it off before validation, so it is shown to the person but never reaches the coordinator or the answer as evidence. It is one task's view, written before synthesis, so it reads quieter than the answer, and a failed task shows none. `progress.limitations` is written for the answering turn and the run record only; the panel reduces it to one plain `coverageNote` and says nothing for routine cases (a provider hiccup on one of thirty calls, a report at its output cap, incomplete usage accounting). A failed task reads "Incomplete", not "Failed" — a failed read is never a user-facing limitation, the worker prompt just routes around it. A question card is the host's own `ask_user` activity and stands on its own.

## Citations

- `validateResearchCitations` accepts plain `[N]` for a registered source and normalises it to `[^N]`, because models write both forms and the chip renderer keys off the footnote form. Unregistered footnote handles become `[unverified source]`; bare bracketed numbers without a registered source stay plain text.

## Search and outage detection

- A query fails only when every configured search provider failed it; fallback between providers happens inside one admitted search ([web search](web-search.md)).
- The budget counts consecutive failed backend queries across all workers (`observeSearch`), once per actual backend completion — never per tool batch, waiter, cache hit, cancellation or refusal. At `searchOutageThreshold` it latches `searchUnavailable`, which ends exploration and dispatch and adds one plain limitation: one failed search is the worker rephrasing, a run of them is the backend down.

## Prompt mechanics

- Stage evidence stays assistant-role data, followed by an application-authored user-role stage request. Never end a coordinator or report prompt on the evidence block — models that disallow assistant prefill reject it. The request lives in protected trailing context so history/active-round compaction and overflow repair cannot drop it.
- Per-call provider timeouts key off stream inactivity (`providerStallMs`), not elapsed time: a worker's searches and reads run inside its own model stream and report progress, so a wall-clock cap would fail productive rounds. The run deadline still bounds every call, and outliving it returns `outcome: "failed"` rather than failing the turn.
- Every exploring turn ends on a user-role soft budget line (`prompts.budgetNotice`, from `budget.remaining()`/`headroom`). It stays last so the prompt prefix keeps its cache, and rides trailing/protected context so compaction budgets it.

## Budgets and caps

- The admin `researchMaxSearchQueries` setting (default 80, range 12–120) caps individual queries across all workers, not tool calls or ordinary chat. It is resolved once when research starts; admission and soft-budget headroom use that same captured value, so admin edits apply only to subsequent runs/retries. Stage prompts stop on evidence-based completion and consequential gaps, not a source-count target — the budget is a ceiling, never a goal.
- Per-phase output caps come from the model's configured `contextLength` (`researchOutputCaps`), with `RESEARCH_LIMITS.*Output` only as ceilings. Task admission reserves an ordinary worker call plus all pending reports at their own caps. Full citation-validated task reports are retained within that generation cap; later stages fit them through evidence compaction rather than a second character cutoff. A report finish reason of `length` signals actual output-limit truncation and adds a limitation while preserving the available report.
- `research/budget.ts` admits actual model calls and batched web targets before execution. The first refused web admission latches `webRefused`, so further rounds and dispatch stop instead of spending model calls on tools that must refuse. Reaching a ceiling is the design, not a limitation: it is returned to the host as an execution bound so the answer can disclose it, but stays out of the user-facing limitation list, which is reserved for coverage that actually failed.
- All workers share one web semaphore, source indexer and URL authority. Worker prose grants no URL authority and never becomes outer assistant text. Child tool/compaction activity nests under the call's activity rather than being sorted independently into prose.

## Evidence projections and progress

- Host history and investigation evidence are separate projections. The host projection retains its start index, injections and checkpoint, including hard truncation and overflow repair; the investigation never resurrects dropped turns. Investigation hands back its current evidence projection only, never reconstructing discarded raw reports. Worker manifests are task-local; inherited sources remain registered but do not become this run's collected evidence merely by being in history.
- `projectResearchProgress` is the explicit durable display boundary for live, terminal and branch snapshots. Reports stay in task columns, never in the call's tool/SSE progress. Unchanged snapshots are suppressed. Limitations collected after the last dispatch round are persisted before the run ends, since nothing outside reads the returned list back into the row. Research compaction keeps the fixed 2k summary and never clears tool results, which workers cite; see [compaction](compaction.md). Research compaction summary bodies stay server-side for checkpoints, never in emitted compaction chunks or public conversation-detail/branch events (ordinary chat compaction summaries remain displayable).

## Usage and ledger

- Research calls checkpoint observed usage; finalization appends one idempotent aggregate chat ledger row keyed by run id, beside the host generation's own row. Compaction uses its own call ID for a separate ledger row, excluded from the chat aggregate. Missing usage means incomplete/unknown cost, not zero. Branch copies terminal display snapshots with fresh IDs only, never calls or ledger entries.
