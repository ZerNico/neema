# Languages

The app reads in English or German. Messages are Paraglide JS: `apps/web/messages/{locale}.json`
compiled into `src/paraglide` (gitignored, written by the Vite plugin and by `pnpm generate`;
`typecheck` compiles it first). Import `m` from `~/paraglide/messages.js` and call a message
like a function: `m.schedules_detail_reload()`.

## Which language

A person's choice lives on their account (`language_settings.chosen`), null meaning
"Automatic". The page mirrors a choice into the `language` cookie, so the first frame and every
request know it without asking the server; without a choice there is no cookie and the browser
decides, on the page through `navigator.languages` and on the server through
`Accept-Language`. Paraglide's own cookie strategy is not used: it stores whatever it first
detected, which would freeze "Automatic" at the language of the first visit
(`src/i18n/choice.ts`). The `_app` route aligns the cookie with the account before rendering
and reloads once when they differ, which is how a choice reaches a second device.

Changing language reloads the page. Nothing re-renders in place, so client code may call a
message anywhere, but a module-level table should hold the message function and call it where
it is shown, which keeps the table readable in tests.

Words sent with no request behind them, like a schedule's mail, use
`LanguageRepo.localeOf(userId)`: the choice, else the browser's language the page last
reported, else English. Text stored for one person to read later (a scheduled run's reason, a
failed queue entry, a fallback chat title) is worded once, in that language, when it is
written. Text several people read from one row, like an integration's listing error, is stored
in English, and text stored where nobody owns it is not stored: the page words it instead.

## Server code builds `Localized`, never strings

`paraglideMiddleware` runs every request in its locale, but Effect fibers do not carry that
context: a scheduler task may run inside another request's. So server code never calls a
message without an explicit locale. It builds a `Localized` (`localized(m.key, inputs)`,
`src/i18n/localized.ts`), and the boundary renders it: `runServerFn` reads the locale while
still in the request and `refusing` words every refusal in it, including `refuse()` decided
inside an effect. An error a person may read carries `reason: Localized`.

## What stays English

The model reads English throughout: system prompts, tool descriptions, tool results, and an
error's reason when it goes to the model (`english(reason)`). Prompts are cached and tuned in
English, and the model answers in the person's language anyway. Logs are English too.

Text the app writes in the person's own name is theirs and in their language, like the request
an "Edit with chat" button puts in the composer.

Wire contracts stay fixed: `NOT_FOUND`, `UNAUTHENTICATED_BODY`, `UNEXPECTED_FAILURE` and other
bodies the client matches by text, slugs, ids, MIME types and file formats.

## Dates and numbers

Formatting for a person passes `getLocale()` to `Intl` and `toLocale*`, never `"en-US"` or
`undefined`: a German page with US dates reads as unfinished. Formats another program reads
(CSV, ISO dates, model context) stay fixed.

## Keys

`<module>_<area>_<meaning>` in snake_case, sorted, one key per meaning in context: "Delete" on a
schedule and "Delete" on a file are two keys when the German differs or might. `common_*` holds
the words every surface shares (Save, Cancel, Close) and nothing else. Plurals use Paraglide's
`plural` selector, never two keys chosen in code. A message never assembles a sentence from
fragments: German word order differs, so the whole sentence is one message with inputs. A link
or emphasis inside a sentence is markup in the message (`{#link}…{/link}`) rendered through
`RichText` (`src/ui/rich-text.tsx`), so German can put it where its word order wants it.

The `i18n/no-literal-text` lint rule (`apps/web/lint/i18n.mjs`) rejects text between tags,
label attributes and toast titles written as literals in `apps/web/src`. Code, keys and product
names take a disable comment that says why.

## Writing German

Translate what the English means in its place, not its words. Read the component: a button
label is an imperative, a toast title says what failed, an empty state invites.

- Address the reader as **du**, lowercase. Imperatives in du form: "Speichere", "Lade neu".
- "Could not save the agent." becomes "Der Agent konnte nicht gespeichert werden."
- Sentence case as in English; nouns keep their capitals.
- Typography: „Anführungszeichen“, apostrophe ’, ellipsis …, non-breaking space before units
  (`10 MB`), decimal comma through `Intl`.
- Terse like the English: no semicolons, no filler. If German runs long, rephrase.
- Keep product nouns from the glossary. Do not translate names: neema, Outlook, Jira, MCP.
