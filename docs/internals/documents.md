# Documents

Documents are editable Markdown artifacts owned by one conversation or one [project](projects.md). They are separate from knowledge documents: they are working material, not indexed source material. A chat's document lives and dies with its answer; a project's is shared by the members and deleted explicitly.

## Storage and transcript boundary

- A document is a ProseMirror tree in a Yjs XML fragment (`default`, the field Tiptap binds). `documents.snapshot` holds its state as of `snapshot_revision` and `document_updates` every batch after it; batches are folded into the snapshot every 64. `content` is that tree serialized as Markdown, rewritten in the transaction that stores each batch, so the model, cards, search and Copy never decode Yjs.
- Browser and server build the tree from one extension list (`documents/editor/extensions.ts`). A node or mark one side lacks would be dropped from everyone's document, so the schema holds only what Markdown can: no underline, colour or alignment. Markdown is the canonical form the serializer writes; parsing and writing it back is stable, and our overrides exist where upstream was not (a backtick in code, a fence in a code block, a pipe in a table cell). Raw HTML stays text, empty paragraphs write nothing, and a numbered list cannot hold tasks.
- `revision` counts stored batches; it tells the model the text moved and guards nothing. Authorization requires both the owning conversation and the person's [document grant](feature-policy.md); a document owned by another account or unavailable under policy is reported as not found.
- `DocumentService` is the only writer, for people and the model alike. It keeps one Y.Doc per document in memory and runs every read-modify-write of one document alone, so memory and rows move together. Any failure after the Y.Doc changed drops the entry, since memory would be ahead of storage, and the next use rebuilds it from the database. This assumes one server process, as the rest of the app does.
- A chat's document records the assistant message that created it. Editing a message before that answer removes the answer and PostgreSQL cascades to its documents. Retrying the creating answer keeps its message id, so the retry transaction explicitly removes its documents before generating again. The confirm dialog names that loss before it happens.
- Document bodies never enter message text, durable tool arguments/results, chunks or compaction summaries. Document tool rows keep only a bounded activity projection such as id, owning conversation, title, revision and outcome. Continuation parts replace tool content with a pointer to application-provided document context.
- Branching copies historical tool rows but never copies canonical document rows. Their references therefore render as inert “From another chat” activity in the branch.

## Model context and writes

- A generation receives a bounded manifest of every conversation document and at most one focused body. The document open in the detail panel supplies the initial focus through `openDocumentId`; an explicit model read or write then becomes the focus for later rounds.
- The focused body is capped independently at 24,000 characters and 200 lines. A truncated entry includes the exact continuation position; `read_chat_document` uses `fromLine` and, for an oversized line, `fromCharacter` so later windows cannot skip source. Other documents contribute metadata only.
- Normal model edits use an exact-match patch on the stored Markdown, which is what the model reads. `old` must occur exactly once under the generation fence: zero matches returns `no_match`, multiple matches returns `ambiguous`, and one match produces the next Markdown. That is parsed and written into the live tree as the smallest change (`updateYFragment`), so blocks that did not change keep their Yjs items and a person typing in one keeps their text and cursor. Replacement is applied the same way. A write drops any empty paragraph a person is about to type into, since Markdown cannot hold one. The model must reread and choose a larger anchor rather than retrying blindly.
- `expectedRevision` on an exact patch is advisory. A stale read is reported, but a unique current anchor can still land beside a person’s unrelated edit. Full replacement is intentionally rare and requires an exact revision. Creation and every write run the generation guard first inside the transaction, so Stop, retry, edit and lost ownership interrupt before anything moves. Lock order is conversation, then document.
- An `edit_document` call is written while its arguments stream. Once `old` has fully arrived and occurs once, its region is found again in the Markdown before each write by the text it now holds, told apart from repeats by up to 80 characters before it, and rewritten to the streamed `new` at most every 80 ms, under a fence that locks the message row (`ensureGenerationLive`), never the conversation. A Markdown offset has no place in the tree, so no assistant cursor shows; the change itself is visible. If the region cannot be told apart any more, because someone typed into it, the preview stops and the decoded call applies normally. The SDK runs the decoded call's handler beside the stream still being read, so one lock per generation orders the two: a handler arriving first claims the call and edits as usual; one arriving later settles the preview under the full fence. A preview no call claims (a refused call) is put back when the round ends; a stopped answer's stays as it stopped.
- Tool-call transport accepts an object with omitted keys even when the advertised JSON schema marks them required. The handler, rather than `LanguageModel.streamText`, then returns its bounded invalid-input correction. This is essential for aliases such as `old_string`, which cannot be repaired if Effect rejects the part first.
- Document context is application data, not instructions. Research mode omits conversation documents in the first version.

## Person edits

- The open editor holds a live connection: a Y.Doc fed by `GET /api/documents/:id/stream` (a `sync` diff against the editor's state vector, then every other editor's batches and cursors) and sending its own through the `pushDocument` server function, batched every 80 ms. Pushes go through a server function rather than a raw route so the CSRF check applies. Document bodies and batches never ride `chat_sync`; cards and lists follow typing through a throttled `document.changed`.
- A local change stays in the outbox until the server acknowledges it. A resend is harmless because Yjs updates are idempotent, so reconnects and lost replies need no sequence numbers. A person's batch locks only the document row, never the conversation: batches arrive several times a second and would otherwise queue ahead of chat writes.
- Concurrent edits merge in the tree: text within a block character by character, structure by node. There is no conflict to resolve. The panel stays editable while the assistant answers, and its edits appear as they are stored. Before send, structured answer, retry, message edit or branch, every connection, including one closed moments ago, flushes its outbox; Stop never waits for it.
- A task's tick is the `checked` attribute of its node, so ticking merges beside any other edit like typing.
- The editor refuses input that would take the serialized Markdown past the size cap, measuring only a document large enough to reach it; a collaborator's accepted change always shows. The server still checks the cap and refuses a batch whose dependencies it lacks, and the editor reconnects and resends.

## UI ownership

- `DocumentOwner` mounts one controller per known id at conversation level, above the virtualized transcript and outside the replaceable panel body. Only the document open in the panel holds a connection, which keeps each tab to one document stream; a closed one lingers until its outbox is acknowledged, so closing the panel or opening another detail cannot discard typing.
- A full document card renders at the creating `create_document` tool row, using that row’s persisted message, turn, call and text-offset coordinates just like other tool activity. Later reads and edits are compact rows. A legacy row without its create call falls back inside its creating answer, never below the transcript.
- The panel title is model-owned. Its actions row is the editor's formatting controls, then a Markdown toggle and Copy, one row that never wraps: the editor portals its toolbar into a slot the owner hands both, and controls that do not fit fold into More. A viewer, or the Markdown view, leaves the slot empty. Documents are removed by rewinding their creating answer rather than through a panel delete control. Copy serializes the local tree and never adds content to the transcript.
- The editor is Tiptap bound to the shared tree through its Collaboration extension, loaded with the first open document rather than the chat. ProseMirror's own history is off: the Yjs undo manager undoes only this editor's changes, never another person's or the assistant's. Formatting comes from the toolbar, a bubble menu over a selection and a `/` menu; every control is a command on the tree, so it syncs like typing. Tasks draw with the app's checkbox through a node view, which changes only the browser's rendering, never the shared schema. A `/` typed by a collaborator never opens this person's menu.
- The Markdown view is read-only: every change goes through the editor, so there is one way text moves. A viewer gets the editor without controls and not editable. Links are only http, https and mailto, and a link carrying any other scheme renders without its address. A click places the caret, so a link opens on Cmd or Ctrl click, or any click for a viewer, always in a new tab. Nothing renders Mermaid or math inside a document.
