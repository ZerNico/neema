# Documents

Documents are editable Markdown artifacts owned by one conversation or one [project](projects.md). They are separate from knowledge documents: they are working material, not indexed source material. A chat's document lives and dies with its answer; a project's is shared by the members and deleted explicitly.

## Storage and transcript boundary

- A document is a Yjs text. `documents.snapshot` holds its state as of `snapshot_revision` and `document_updates` every batch after it; batches are folded into the snapshot every 64. `content` is the same text as Markdown, rewritten in the transaction that stores each batch, so the model, cards and search never decode Yjs. `revision` counts stored batches; it tells the model the text moved and guards nothing. Authorization requires both the owning conversation and the person's [document grant](feature-policy.md); a document owned by another account or unavailable under policy is reported as not found.
- `DocumentService` is the only writer, for people and the model alike. It keeps one Y.Doc per document in memory and runs every read-modify-write of one document alone, so memory and rows move together. Any failure after the Y.Doc changed drops the entry, since memory would be ahead of storage, and the next use rebuilds it from the database. This assumes one server process, as the rest of the app does.
- A chat's document records the assistant message that created it. Editing a message before that answer removes the answer and PostgreSQL cascades to its documents. Retrying the creating answer keeps its message id, so the retry transaction explicitly removes its documents before generating again. The confirm dialog names that loss before it happens.
- Document bodies never enter message text, durable tool arguments/results, chunks or compaction summaries. Document tool rows keep only a bounded activity projection such as id, owning conversation, title, revision and outcome. Continuation parts replace tool content with a pointer to application-provided document context.
- Branching copies historical tool rows but never copies canonical document rows. Their references therefore render as inert “From another chat” activity in the branch.

## Model context and writes

- A generation receives a bounded manifest of every conversation document and at most one focused body. The document open in the detail panel supplies the initial focus through `openDocumentId`; an explicit model read or write then becomes the focus for later rounds.
- The focused body is capped independently at 24,000 characters and 200 lines. A truncated entry includes the exact continuation position; `read_chat_document` uses `fromLine` and, for an oversized line, `fromCharacter` so later windows cannot skip source. Other documents contribute metadata only.
- Normal model edits use an exact-match patch. `old` must occur exactly once in the current text under the generation fence: zero matches returns `no_match`, multiple matches returns `ambiguous`, and one match applies to the live Y.Doc as the smallest change between `old` and `new`, so a person typing nearby keeps their text and cursor. Replacement is applied the same way. The model must reread and choose a larger anchor rather than retrying blindly.
- `expectedRevision` on an exact patch is advisory. A stale read is reported, but a unique current anchor can still land beside a person’s unrelated edit. Full replacement is intentionally rare and requires an exact revision. Creation and every write run the generation guard first inside the transaction, so Stop, retry, edit and lost ownership interrupt before anything moves. Lock order is conversation, then document.
- An `edit_document` call is written while its arguments stream. Once `old` has fully arrived and occurs once, the region is pinned by a left-associated relative position and rewritten to the streamed `new` at most every 80 ms, under a fence that locks the message row (`ensureGenerationLive`), never the conversation. An "Assistant" cursor marks it. The SDK runs the decoded call's handler beside the stream still being read, so one lock per generation orders the two: a handler arriving first claims the call and edits as usual; one arriving later settles the preview under the full fence. A preview no call claims (a refused call) is put back when the round ends; a stopped answer's stays as it stopped.
- Tool-call transport accepts an object with omitted keys even when the advertised JSON schema marks them required. The handler, rather than `LanguageModel.streamText`, then returns its bounded invalid-input correction. This is essential for aliases such as `old_string`, which cannot be repaired if Effect rejects the part first.
- Document context is application data, not instructions. Research mode omits conversation documents in the first version.

## Person edits

- The open editor holds a live connection: a Y.Doc fed by `GET /api/documents/:id/stream` (a `sync` diff against the editor's state vector, then every other editor's batches and cursors) and sending its own through the `pushDocument` server function, batched every 80 ms. Pushes go through a server function rather than a raw route so the CSRF check applies. Document bodies and batches never ride `chat_sync`; cards and lists follow typing through a throttled `document.changed`.
- A local change stays in the outbox until the server acknowledges it. A resend is harmless because Yjs updates are idempotent, so reconnects and lost replies need no sequence numbers. A person's batch locks only the document row, never the conversation: batches arrive several times a second and would otherwise queue ahead of chat writes.
- Concurrent edits merge character by character; there is no conflict to resolve. The panel stays editable while the assistant answers, and its edits appear as they are stored. Before send, structured answer, retry, message edit or branch, every connection, including one closed moments ago, flushes its outbox; Stop never waits for it.
- Rendered GFM task controls are mapped back to source by ordinal among task-list lines. Streamdown receives rendering-only sanitized marker spans so nested and numbered items retain that ordinal. A tick is a change to the single marker character, so it merges beside any other edit.
- The editor refuses input past the size cap itself; the server still checks it, and refuses a batch whose dependencies it lacks, and the editor reconnects and resends.

## UI ownership

- `DocumentOwner` mounts one controller per known id at conversation level, above the virtualized transcript and outside the replaceable panel body. Only the document open in the panel holds a connection, which keeps each tab to one document stream; a closed one lingers until its outbox is acknowledged, so closing the panel or opening another detail cannot discard typing.
- A full document card renders at the creating `create_document` tool row, using that row’s persisted message, turn, call and text-offset coordinates just like other tool activity. Later reads and edits are compact rows. A legacy row without its create call falls back inside its creating answer, never below the transcript.
- The panel title is model-owned. Its only actions are an animated Preview/Source switch and Copy; documents are removed by rewinding their creating answer rather than through a panel delete control.
- Preview shares the assistant Markdown renderer and changes only GFM task controls. Markdown still passes through Streamdown’s sanitizer. Copy uses the current local source and never adds content to the transcript.
- Source is CodeMirror bound through `y-codemirror.next`, loaded with the first source view rather than the chat. CodeMirror's own history is off: the Yjs undo manager undoes only this editor's changes, never another person's or the assistant's.
